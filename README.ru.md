### [⬇ Скачать ZipMount для Windows](https://github.com/marlogg74mp/zipmount/releases/latest)

Возьмите на странице выпуска **`ZipMount-Setup-<версия>.exe`** и запустите —
WinFsp уже внутри. 64-битная Windows 10 (версия 2004 или новее) или Windows 11.
Подробнее — в разделе [Установка](#установка) · [сайт](https://marlogg74mp.github.io/zipmount/) ·
на Linux — [сборка из исходников](#linux)

![ZipMount](docs/hero.jpg)

Монтирует архив как обычный диск Windows — только для чтения, без распаковки.
В Проводнике появляется том, по которому работают навигация, поиск по именам,
открытие файлов любыми программами и копирование наружу. Архив остаётся одним
файлом; содержимое распаковывается лениво.

Поддерживаются **zip**, **7z**, **tar** и **tar.gz**; **rar** — в сборке,
сделанной своими руками ([почему](#про-rar-нет-в-официальных-сборках)).

```
zipmount mount D:\data\archive.7z Z:
```

Говорит по-английски, по-русски, по-китайски, по-японски, по-корейски,
по-португальски, по-испански и по-немецки — в командной строке, в контекстном
меню и в установщике ([как выбирается язык](#языки)).

Это личный проект, который развивается в свободное время. Самые полезные
сообщения об ошибках — с архивом, на котором она воспроизводится.

## Зачем, если есть 7-Zip

7-Zip и «Сжатые ZIP-папки» — это оболочки над архивом: ни буквы диска, ни
доступа из произвольных программ по обычному пути, ни нормального
рекурсивного поиска. ZipMount поднимает настоящий том через
[WinFsp](https://winfsp.dev/) — тот же механизм, на котором работают rclone,
sshfs-win и Google Drive для десктопа.

## Установка

Свежий установщик — в разделе
[Releases](https://github.com/marlogg74mp/zipmount/releases/latest). Запустите
**`ZipMount-Setup-<версия>.exe`** и согласитесь с запросом прав. Он ставит
ZipMount в `C:\Program Files\ZipMount`, добавляет каталог в `PATH` и
настраивает современное контекстное меню — в том числе доверяет сертификату
пакета, и отдельного запроса прав для этого не нужно: установщик и так
работает с правами администратора.

Внутри он несёт WinFsp — драйвер, через который Windows видит архив как диск, —
и ставит его **только если тот отсутствует**. Это официальный установщик с
winfsp.dev, без изменений и с подписью автора; уже установленный драйвер не
трогается, в том числе если он новее.

Удаление из «Установленных приложений» уносит ZipMount целиком, вместе с
сертификатом. **WinFsp остаётся.** Он общий — на нём работают rclone и
sshfs-win, — и унести его с собой значило бы сломать их без предупреждения.
Удалить его отдельно можно там же, в том же списке.

Две вещи, о которых честнее сказать сразу. Установщик не подписан, поэтому в
окне контроля учётных записей будет «Издатель: неизвестно», а свежескачанная
копия вызовет предупреждение SmartScreen; убрать это можно только настоящим
сертификатом для подписи кода, самоподписанный не подойдёт. До тех пор скачанное
можно проверить двумя способами: сверить с `SHA256SUMS.txt` из того же выпуска
или попросить GitHub подтвердить, что файл собран процессом выпуска этого
репозитория из помеченного тегом коммита:

```
gh attestation verify ZipMount-Setup-<версия>.exe --repo marlogg74mp/zipmount
```

И если регистрация меню не
удастся, установка всё равно пройдёт — меню приятное дополнение, а не условие
работы, и встало ли оно, скажет `zipmount doctor`.

Рядом выкладывается `ZipMount-<версия>.msi` — на случай, когда WinFsp уже стоит
и удобнее обычный пакет: например, для раздачи групповой политикой.

Если меню до этого настраивалось вручную, сначала выполните
`zipmount shell-uninstall`, иначе пункт размонтирования покажется дважды.

### Из исходников

```
winget install WinFsp.WinFsp
cargo build --release
```

Проверить готовность: `zipmount doctor`. Поддержка rar включается ключом
`--features zipmount/rar` — только для себя, см.
[ниже](#про-rar-нет-в-официальных-сборках).

Для `shell-install --modern` дополнительно нужен Windows SDK — оттуда берутся
`makeappx` и `signtool`:

```
winget install Microsoft.WindowsSDK.10.0.26100
```

Сборка не требует LLVM: вендоренная копия `winfsp-sys` в `vendor/` использует
готовые биндинги вместо запуска bindgen (см. комментарии в её `build.rs`).

### Linux

Пакета пока нет — собирается из исходников. Монтирование идёт через FUSE,
который любой распространённый дистрибутив поставляет как `fuse3`: устройство
`/dev/fuse` и помощник `fusermount3`. Самой сборке не нужно ничего, кроме Rust:
ни libfuse, ни `-dev`-пакетов.

```
sudo apt install fuse3            # Debian, Ubuntu; в других — dnf или pacman
cargo build --release
./target/release/zipmount mount archive.7z
```

Без указания каталога архив монтируется в `~/ZipMount/<имя архива>` — каталог
создаётся под монтирование и удаляется после; монтирование в домашней папке
файловые менеджеры показывают на боковой панели. `zipmount unmount`,
`fusermount3 -u` или Ctrl+C в терминале, где монтировали, — всё снимает его
чисто. `zipmount mounts` читает собственный список ядра, так что ничего не
устаревает, если процесс убит. Команды по архиву (`ls`, `find`, `grep`, `info`,
`verify`) работают ровно как на Windows, с FUSE или без. Меню файлового
менеджера пока нет.

На macOS команды по архиву тоже собираются и работают; монтирование —
следующий шаг.

### Сборка установщиков

```
powershell -ExecutionPolicy Bypass -File tools\build-installer.ps1
```

Нужны Windows SDK и WiX 4 с двумя расширениями. Версию указывать обязательно:
без неё ставится свежая ветка, которую WiX 4 загрузить не может и молча
помечает «damaged».

```
dotnet tool install --global wix
wix extension add WixToolset.Bal.wixext/4.0.5
wix extension add WixToolset.Util.wixext/4.0.5
```

Порядок внутри скрипта не случаен: сначала программа, потом пакет контекстного
меню — его собирает и подписывает сама программа, — потом MSI, и только потом
связка, которая несёт MSI внутри себя. На машине, куда программа ставится, SDK
нет, и собрать пакет там нечем. Установщик WinFsp скачивается один раз в
`target/deps`, и его подпись проверяется перед тем, как он попадёт в связку.

Версия установщика — версия из `Cargo.toml` и четвёртым полем число коммитов:
`0.2.0.37`. Это не украшение: с неизменной версией установщик не считает новую
сборку обновлением, и каждая установка добавляет ещё одну запись в
«Установленные приложения» вместо замены прежней. Раньше хватало одного числа
коммитов, но в свежей копии истории счёт начинается заново, а меньшая версия
перестаёт обновлять программу. Установщик пакетов сравнивает только три поля,
поэтому пакету разрешено обновление той же версией; связка сравнивает все
четыре.

### Непрерывная интеграция и выпуски

Каждый push в `master` и каждый pull request проверяет форматирование, clippy
с предупреждениями как ошибками и тесты — дважды: для официальной сборки и для
сборки с `rar`, которая никогда не выкладывается, но должна работать у тех, кто
собирает её сам. См. `.github/workflows/ci.yml`.

Выпуск — это тег:

```
# поднять version в [workspace.package] в Cargo.toml, закоммитить, затем:
git tag v0.2.0
git push origin v0.2.0
```

Процесс выпуска (`.github/workflows/release.yml`) отвергает тег, не совпадающий
с `Cargo.toml`, прогоняет тесты, собирает оба установщика, прикладывает к ним
аттестацию происхождения сборки и создаёт **черновик** выпуска с установщиками
и `SHA256SUMS.txt`. Публикуется он одной кнопкой на странице выпуска: выпуск
публичен и приходит в уведомления подписчикам, так что последний взгляд — за
человеком.

Пакет контекстного меню подписывается самоподписанным сертификатом, который
создаётся прямо на сборочной машине; закрытый ключ исчезает вместе с ней, так
что ни один ключ не переживает выпуск, который им подписан.

То же можно сделать вручную:

```
powershell -ExecutionPolicy Bypass -File tools\build-installer.ps1
powershell -ExecutionPolicy Bypass -File tools\publish-release.ps1
```

Второму скрипту нужен GitHub CLI, вошедший в аккаунт владельца репозитория
(`gh auth login`). Пакет, собранный не из той версии, что в `Cargo.toml`, он
выкладывать откажется — иначе вчерашняя сборка могла бы уйти под сегодняшним
номером. Ключ `-WhatIf` показывает, что будет выложено, и SHA256 каждого файла,
ничего не трогая.

## Команды

| Команда | Что делает |
|---|---|
| `zipmount mount <архив> [Z:]` | смонтировать; без буквы берётся первая свободная |
| `zipmount unmount <Z:\|архив>` | размонтировать |
| `zipmount mounts` | что сейчас смонтировано |
| `zipmount ls <архив> [путь]` | содержимое каталога, `-r` — всё дерево |
| `zipmount find <архив> <маска>` | поиск по именам |
| `zipmount grep <архив> <регулярка>` | поиск по содержимому, минуя файловую систему |
| `zipmount verify <архив>` | сквозная проверка чтения по CRC32 из самого архива |
| `zipmount info <архив>` | сводка; для 7z — число solid-блоков, для tar.gz — занятая память |
| `zipmount doctor` | проверка готовности к монтированию |
| `zipmount shell-install [--modern]` | добавить пункты в контекстное меню Проводника |
| `zipmount shell-uninstall` | убрать их |
| `zipmount language [код\|auto]` | показать или выбрать язык программы |

У `mount` есть `--detach` (смонтировать в фоне и вернуть управление) и
`--open` (открыть диск в Проводнике). Их использует контекстное меню.

Формат определяется по сигнатуре файла, а не по расширению. Точкой монтирования
может быть буква (`Z:`) или путь к пустому каталогу NTFS.

Любая команда принимает `-p` (запросить пароль скрытым вводом) и
`--password-stdin` (прочитать пароль из стандартного ввода).

## Языки

| Код | Язык |
|---|---|
| `en` | English — язык по умолчанию и эталон |
| `ru` | Русский |
| `zh-CN` | 简体中文 |
| `ja` | 日本語 |
| `ko` | 한국어 |
| `pt-BR` | Português (Brasil) — достаётся и Португалии |
| `es` | Español |
| `de` | Deutsch |

Язык определяется в таком порядке:

1. `ZIPMOUNT_LANG` — на одну команду или один сеанс консоли;
2. выбор, сохранённый командой `zipmount language <код>`, — лежит в
   `HKCU\Software\ZipMount\Language` (на Linux — в
   `~/.config/zipmount/language`, на macOS — в
   `~/Library/Application Support/ZipMount/language`);
3. язык интерфейса Windows, в порядке предпочтений пользователя (на Linux и
   macOS — локаль: `LANGUAGE`, `LC_ALL`, `LC_MESSAGES`, `LANG`, а затем
   собственный список предпочитаемых языков macOS);
4. английский.

```
zipmount language          # какой язык действует сейчас и почему
zipmount language ja       # выбрать японский
zipmount language auto     # снова следовать языку Windows
```

Выбор языка доходит и до контекстного меню. Современное меню спрашивает тексты
при каждой отрисовке, поэтому подхватывает язык сразу. Пункты в реестре —
статичные строки, их `zipmount language` переписывает. А для пункта на диске,
который установщик пишет в `HKEY_LOCAL_MACHINE` и который пользователю без
повышения прав не изменить, кладётся копия с новым текстом в
`HKEY_CURRENT_USER` — Проводник предпочитает её. Если ZipMount потом удалить,
копия никому не мешает: её `AppliesTo` показывает пункт только на томах
ZipMount, а без программы их не бывает.

Окно установщика само следует языку интерфейса Windows.

Русский перевод родной, остальные сделаны с помощью машины, и правки от
носителей очень приветствуются. Все сообщения лежат в
`crates/zipmount-i18n/locales/<код>.ftl`, в синтаксисе
[Fluent](https://projectfluent.org/). Fluent — из-за множественного числа:
русскому нужны три формы («1 файл», «2 файла», «5 файлов») по правилам CLDR, а
форматы попроще этого не выражают. Тесты требуют, чтобы в каждом языке был
ровно тот же набор сообщений, что в английском, — пропущенный или опечатанный
идентификатор роняет сборку, а не всплывает у пользователя в консоли. Новый
язык — это один файл `.ftl`, одна строка в `LANGUAGES` и для установщика
каталог `installer/locales/<код>/` с `thm.wxl` и `about.txt`.

Собственные сообщения clap об ошибках («unexpected argument», «[default: …]»)
остаются английскими: перевести их clap не позволяет.

## Контекстное меню Проводника

```
zipmount shell-install --modern   # основное меню Windows 11
zipmount shell-install            # только реестр, без администратора
zipmount shell-uninstall          # убрать любой из вариантов
```

Четыре пункта, одинаковые в обоих вариантах:

| Пункт | Где появляется |
|---|---|
| Смонтировать как диск | на архиве `.zip .7z .tar .gz .tgz` (и `.rar` в сборке с rar) |
| Смонтировать на букву | там же, подменю с выбором |
| Найти в архиве… | там же, поиск по содержимому в отдельной консоли |
| Размонтировать (ZipMount) | на папке внутри смонтированного тома и на пустом месте в нём |

Разница — куда именно Windows их кладёт.

### Почему современный вариант устроен сложнее

В Windows 11 команды из реестра в основное контекстное меню не попадают: они
живут под «Показать дополнительные параметры» или сразу по Shift+правый клик.
В основное меню система пускает только обработчики `IExplorerCommand`,
объявленные пакетом с идентичностью приложения. Отсюда три части:

**Библиотека `zipmount_shell.dll`** реализует `IExplorerCommand` и живёт внутри
процесса Проводника. Она ничего не знает про архивы — не зависит даже от
`zipfs-core`. Её работа целиком: показать пункт и запустить `zipmount.exe`,
который лежит рядом. Открытие архива стоит времени и памяти, а платил бы за
это Проводник.

**Разреженный (sparse) пакет** даёт идентичность, не затаскивая программу
внутрь себя: в `.msix` лежит только манифест и плитки, а `zipmount.exe` и
библиотека остаются обычными файлами в каталоге «внешнего содержимого».
Из командной строки всё работает как раньше.

**Подпись и одно действие с правами администратора.** Windows принимает пакет
только с подписью, а доверие к сертификату — решение уровня машины. Поэтому
установка создаёт самоподписанный сертификат (в личном хранилище пользователя,
без прав), подписывает им пакет и один раз просит повышения прав, чтобы
положить сертификат в доверенные. Сертификат остаётся видимым файлом рядом с
программой, а команда для его удаления печатается при `shell-uninstall`.

Что это даёт помимо основного меню: подменю букв собирается **в момент
показа**, поэтому в нём перечислены только свободные буквы. Реестр так не
умеет — там список фиксируется при установке и быстро начинает врать.

Чего не даёт: размонтирования по клику на самом диске. Схема манифеста
разрешает всего четыре цели — расширение файла, `*`, `Directory` и
`Directory\Background`, — диска среди них нет. `Directory` был испробован на
случай, если Windows считает корень диска папкой; не считает — ровно так же,
как реестровые `Directory`-глаголы никогда не появляются на дисках. Поэтому
пункт размонтирования в современном варианте живёт на папках внутри тома и на
пустом месте в нём, а на самом диске его по-прежнему ставит реестр —
единственный пункт, который остаётся под «дополнительными параметрами».

Проверить, что всё срослось: `zipmount doctor` не просто смотрит список
установленных пакетов, а создаёт COM-объект обработчика и спрашивает у него
заголовок пункта. Между зарегистрированным пакетом и нарисованной строкой
лежит ещё загрузка библиотеки, и ошибка там выглядит как молча пропавший
пункт.

### Три решения в реестровом варианте

**Пункты добавляются в `SystemFileAssociations`, а не в ProgID расширения.**
ProgID у архивов обычно занят архиватором, и дописывать туда свои команды
значило бы влезать в чужую регистрацию. `SystemFileAssociations` — штатное
место именно для добавления глаголов к типу файла, не трогая ассоциацию.

**В подменю выбора буквы перечислены все буквы, а не только свободные** — по
причине выше. Выбор занятой буквы даёт понятную ошибку, это честнее
устаревшего списка.

**Пункт размонтирования ограничен нашими томами** условием
`AppliesTo = System.Volume.FileSystem:ZipFS`. Без него он висел бы на каждом
диске в системе.

Всё пишется только в `HKEY_CURRENT_USER`: прав администратора не нужно.

### Как это устроено внутри

Из меню диск монтируется в фоне, поэтому нужен учёт: какая буква какому архиву
соответствует и каким процессом занята. Список лежит в
`%LOCALAPPDATA%\ZipMount\mounts.tsv` и при каждом чтении перепроверяется.

Остановка идёт не убийством процесса, а именованным событием: процесс
монтирования ждёт либо Ctrl+C, либо сигнала от `unmount`, и в обоих случаях
успевает корректно отдать том.

Современная установка копирует программу в `C:\ProgramData\ZipMount\bin` и
показывает пакету именно эту копию. Каталог сборки не годится: Проводник
держит загруженную библиотеку и не даёт её перезаписать, да и `cargo clean`
не должен ломать меню. Имя библиотеки содержит отпечаток её содержимого —
перезаписывать занятый файл не нужно, новая сборка просто ложится рядом.
**После пересборки повторите `zipmount shell-install --modern`**, иначе меню
продолжит запускать прошлую копию.

## Про поиск: почему `grep` отдельной командой

Поиск по содержимому **через файловую систему** (галка «содержимое файлов» в
Проводнике, `findstr /s`) на гигабайтах неизбежно медленный: ядро дёргает
колбэки мелкими чтениями, файлы обрабатываются по одному, и архив
распаковывается заново на каждый поиск. Это свойство способа, а не реализации.

Поэтому поиск разведён на два уровня:

* **по именам** — мгновенно, в том числе в Проводнике: дерево целиком в памяти;
* **по содержимому** — командой `zipmount grep`, которая работает с архивом
  напрямую, параллельно, движком ripgrep.

### Шаблон — это подстрока, а не регулярка

Это сознательный выбор против привычки grep, и вот почему. На настоящем архиве
логов поиск `[ERROR]` в режиме регулярного выражения совпал с **29 748 файлами
из 30 778**: как регулярка это «любая из букв E, R, O». Никакой ошибки при
этом не выдаётся — просто приходит осмысленно выглядящая чушь. Для строк вида
`[ERROR]`, `app.config` или `GET /api/v1` такое происходит постоянно.

Поэтому по умолчанию шаблон ищется буквально, а регулярки включаются явно:

```
zipmount grep archive.7z "[ERROR]"           # ищет именно [ERROR]
zipmount grep archive.7z "ERROR|WARN" --regex
```

### Ключи поиска

| Ключ | Что делает |
|---|---|
| `-l` | только пути (сразу в виде `Z:\...`, чтобы открывать) |
| `-c` | сколько совпадений в каждом файле |
| `-i` | игнорировать регистр |
| `-C N` / `-A N` / `-B N` | строки контекста вокруг совпадения |
| `--max-count N` | не больше N совпадений в одном файле |
| `--max-total N` | не больше N строк во всём выводе |
| `--path <путь>` | искать только внутри ветки архива |
| `--glob "*.log"` | ограничить маской имени |
| `--copy-to <каталог>` | извлечь все совпавшие файлы разом |

Вывод строк устроен как в grep: двоеточие после номера у самого совпадения,
дефис — у строки контекста.

`--path` и `--glob` в 7z экономят не только сканирование, но и распаковку:
блоки, в которых нет ни одной подходящей записи, не разворачиваются вовсе.
На архиве логов ограничение одной веткой сокращает поиск с 2,23 с до 0,84 с —
разворачивается один solid-блок из трёх.

## Пять форматов — три модели доступа

Различие не спрятано за общим интерфейсом, потому что от него напрямую зависит
поведение: время открытия, расход памяти и то, какой порядок чтения дешёвый.

**zip**: каждая запись сжата независимо, читать можно пофайлово. Путей чтения
три — единый путь «распаковать запись целиком» сломался бы на файле, который
больше памяти:

* `stored` — срез отображённого в память файла, без копирования и распаковки;
* мелкий `deflate` (по умолчанию до 8 МБ) — распаковка целиком в LRU-кэш
  с байтовым бюджетом, дальше срезы из памяти;
* крупный `deflate` — потоковый декодер с checkpoint-индексом: вперёд идёт
  потоком при постоянной памяти, назад прыгает на ближайшую контрольную точку.

### Checkpoint-индекс: как читать deflate назад

Deflate нельзя читать с произвольного места: распаковка каждого байта зависит
от предыдущих 32 КБ. Наивное решение — перезапускать поток с начала — на
крупной записи превращает произвольный доступ в сотни мегабайт лишней работы.

Решение — техника `zran` из примеров zlib: раз в несколько мегабайт
запоминается состояние, достаточное для возобновления (позиция **в битах**
внутри сжатого потока и 32 КБ уже распакованных данных в качестве словаря).
Тогда любая перемотка стоит не больше одного шага между точками.

Измерено на одной записи в 315 МБ, чтение вразнобой блоками по 64 КБ:

| | Время | Скорость |
|---|---|---|
| Перезапуск потока | 245,93 с | 1 МБ/с |
| Checkpoint-индекс | **1,30 с** | 231 МБ/с |

Это **в 189 раз** быстрее. Последовательное чтение при этом не изменилось
(1192 МБ/с), и разрыв между произвольным и последовательным доступом упал
с полутора порядков до пяти раз.

Две вещи оказались важнее, чем кажется:

**Шаг между точками нельзя фиксировать.** Сначала он был выставлен в 16 МБ —
и на записи в 12 МБ не дал ни одной точки, то есть индекс получился пустым и
не менял ничего. Затем шаг привязывался к числу точек, и на 315 МБ каждая
перемотка стоила 9 МБ. Работающая политика — привязка к памяти индекса: точек
`размер/шаг`, каждая по 32 КБ, отсюда шаг из потолка в 32 МБ на запись.

**Индекс строится лениво.** Проход стоит одной полной распаковки, поэтому он
запускается только тогда, когда чтение назад действительно случилось, — и
только для записей крупнее 4 МБ, где перезапуск дороже индекса.

Восстановление состояния требует `inflatePrime`, `inflateSetDictionary` и
`inflateReset2`, которых нет в удобных обёртках вроде `flate2`. Они взяты из
`libz-rs-sys` — это тот же C-совместимый интерфейс zlib, но реализованный на
Rust, поэтому в сборку не приезжает ни C-компилятор, ни внешняя библиотека.

**7z**: записи склеены в solid-блоки, и чтобы достать один файл, нужно
развернуть его блок с начала. Отсюда два режима:

* произвольный доступ (смонтированный диск) — через кэш развёрнутых блоков.
  У кэша одно особое правило: **самый свежий блок не вытесняется никогда**,
  даже если один превышает бюджет, иначе каждое чтение разворачивало бы его
  заново. Бюджет задаётся ключом `--cache-mb`, по умолчанию 6 ГБ;
* сплошной просмотр (поиск, проверка) — потоком по блоку, без кэша, с
  постоянной памятью. Для solid-архива это ещё и оптимальный порядок чтения,
  поэтому `grep` по 5,6 ГБ укладывается в секунды при скромной памяти.

Ограничения области поиска (`--path`, `--glob`) здесь экономят не только
сканирование, но и распаковку: блоки, в которых нет ни одной подходящей
записи, не разворачиваются вовсе.

Вопреки ожиданиям, solid не обязательно значит медленно. У хорошо сжимаемых
данных декодер читает мало входных байт: в замерах выше архив логов сжат в
37 раз, поэтому блок в 2 ГБ разворачивается примерно за секунду.

**tar**: самый удачный случай из всех. Данные каждого файла лежат непрерывным
куском, поэтому чтение — это срез отображённого в память архива: ни распаковки,
ни копирования, ни кэша. Плата за это одна: оглавления в формате нет вовсе,
и чтобы узнать состав, приходится пройти всю цепочку заголовков. Но проход
идёт только по ним, перескакивая через данные, поэтому гигабайтный архив
открывается за сотые доли секунды.

**rar**: по модели доступа ближе всего к 7z — архив может быть solid, и тогда
чтение одного файла требует пройти весь предшествующий поток. Отсюда те же два
режима: произвольный доступ через кэш (у solid-архива первый же промах
наполняет его целиком, потому что один проход дешевле прохода на каждый файл),
сплошной просмотр — одним последовательным проходом. Обычный, не solid архив
проще: запись читается адресно, пропуск предыдущих не требует их распаковки.

**tar.gz**: та же развилка, что у 7z, доведённая до предела — solid-поток ровно
один на весь архив. Точек входа нет, поэтому даже для получения списка файлов
поток разворачивается целиком, один раз при открытии; дальше архив ведёт себя
как обычный tar. Занятая память равна распакованному размеру и показывается
в `zipmount info`; потолок задаётся ключом `--cache-mb`, и при его превышении
открытие честно прерывается с понятным сообщением, а не съедает всю память.

Это единственное место, где checkpoint-индекс напрашивается, но пока не
применён: он позволил бы держать в памяти индекс вместо всего архива и снял
бы ограничение на размер `.tar.gz`. Цена — потеря чтения срезом без
копирования, на котором сейчас держится скорость поиска по tar.

## Архивы под паролем

Поддерживаются все три схемы, которые встречаются на практике:

| Схема | Где | Как проверяется |
|---|---|---|
| WinZip AES-128/192/256 | zip, метод 99 | HMAC-SHA1 по шифротексту |
| ZipCrypto | zip, наследие 1990-х | проверочный байт заголовка |
| AES-256 | 7z, включая шифрованное оглавление (`-mhe=on`) | CRC32 записи |
| AES-256 | rar (в сборке с rar), включая шифрованное оглавление (`-hp`) | проверяет сам UnRAR |

ZipCrypto криптографически слаба и вскрывается атакой по открытому тексту.
ZipMount такие архивы только **читает** и никогда не создаёт.

### Как передать пароль

```
zipmount ls archive.7z -p                    # запросит скрытым вводом
type pw.txt | zipmount ls archive.7z --password-stdin
```

Ключа вида `--password=ЗНАЧЕНИЕ` намеренно нет. Пароль в командной строке
оседает в истории оболочки и виден в списке процессов другим пользователям
системы — это не та цена, которую стоит платить за экономию одного нажатия.

`--password-stdin` читает **байты**, а не текст: пароль не обязан быть валидным
UTF-8. Для паролей с не-ASCII символами надёжнее `-p`: там кодировка ввода
известна, а при передаче через конвейер она зависит от кодовой страницы консоли.

### Две особенности, о которых стоит знать

**У записей WinZip AE-2 нет CRC32.** Поле в заголовке намеренно обнулено:
целостность там подтверждает HMAC, посчитанный при расшифровке, а не
контрольная сумма. Поэтому `zipmount verify` показывает такие записи отдельной
строкой «без контрольной суммы в архиве» — это не ошибка и не пропуск
проверки: повреждение поймает HMAC.

**Оглавление 7z тоже может быть зашифровано** (ключ `-mhe=on` у 7-Zip). Тогда
пароль нужен уже для того, чтобы увидеть список файлов, а не только прочитать
их содержимое.

## Кодировки имён

Касается только zip: в 7z имена всегда Unicode. Если zip собран без флага UTF-8
(так делает WinRAR на русской Windows), имена лежат в CP866 или CP1251, и
наивная реализация показывает кракозябры. ZipMount определяет кодировку
эвристически и уважает Info-ZIP Unicode Path extra field. Переопределить:
`--encoding auto|utf8|cp866|cp1251`.

## Проверка

```
python tools\make-test-archives.py          # тестовые архивы, включая «злые»
cargo test --workspace
zipmount verify testdata\big.zip --random   # сверка чтения с CRC из архива
```

Тестовые архивы намеренно содержат то, на чём ломаются наивные реализации:
кириллицу в CP866 без флага UTF-8, отсутствующие записи родительских каталогов,
дубликаты имён, различающиеся только регистром, зарезервированные имена
устройств (`CON.txt`), символы, недопустимые в Windows, zip-slip (`../../evil`),
`stored`-запись и запись крупнее порога материализации.

Для tar генерируются оба формата длинных имён — GNU (`L`-блок) и PAX
(`ключ=значение`), — потому что разбор ломается именно на них: в ustar-полях
длинный кириллический путь просто не помещается.

## Про rar: нет в официальных сборках

RAR закрыт, и единственная полная реализация распаковки — исходники UnRAR от
RARLAB. Альтернативы проверены и отвергнуты:

| Вариант | Почему нет |
|---|---|
| `rar` (нативный на Rust, MIT) | умеет только несжатые RAR5 (`SAVE`), RAR4 не умеет вовсе |
| `unrar-rs` (нативный, полный) | при первой проверке был под GPL-3.0-or-later, свежие версии — под нестандартной лицензией |
| `unrar` (обёртка над UnRAR) | **выбран**: полная поддержка, обёртка под MIT |

Условия UnRAR разрешают использовать код для чтения архивов без ограничений и
бесплатно, но запрещают делать на его основе совместимый упаковщик. ZipMount
только читает — но проблема в самом ограничении. Слой монтирования линкует
крейт `winfsp`, а он под чистой GPLv3, которая дополнительных ограничений такого
рода не допускает; FLOSS-исключение самого WinFsp вдобавок требует, чтобы
программа не линковалась и не распространялась вместе с несвободным кодом.

Поэтому rar — cargo-фича, **выключенная по умолчанию**, и в выложенных
установщиках UnRAR нет. Для себя собрать с rar можно:

```
cargo build --release --features zipmount/rar
```

Распространять такую сборку — нельзя. Без фичи rar-архив всё равно узнаётся по
сигнатуре и получает внятную ошибку, а не «формат не определён», а
контекстное меню на `.rar` не предлагает себя вовсе.

Фича заодно приносит в сборку C++: UnRAR — единственная зависимость проекта,
требующая компилятора C++. В остальных местах он не нужен даже там, где
напрашивался: checkpoint-индекс использует zlib, реализованный на Rust.

## Ограничения

Только чтение. Не поддерживаются: запись в архив, многотомные архивы,
вложенные архивы, а из сжатых tar — только gzip (не bz2/xz/zst).

**У tar нет контрольных сумм содержимого** — в заголовке есть сумма только
самого заголовка. Поэтому `zipmount verify` на tar проверяет лишь то, что все
записи читаются целиком и не выходят за границы архива. Для `tar.gz` к этому
добавляется CRC32 всего потока, который сверяется при распаковке.

**RAR5 намеренно искажает контрольную сумму** у файлов, зашифрованных без
шифрования оглавления, — чтобы по ней нельзя было проверять угаданный пароль,
не пытаясь расшифровать данные. `verify` такие записи читает, но не сверяет, и
прямо об этом пишет. В RAR4 этого приёма нет, там сумма проверяется как обычно.

**RAR4 проверен только на чтение.** Создать такой архив локально не вышло:
RAR 7.23 умеет их читать, но больше не умеет создавать. Проверка сделана на
образцах, которые везёт с собой крейт `unrar`.

Отдельно о непроверенном: расшифровка zip AES с не-ASCII паролем реализована
по спецификации (байты пароля в UTF-8), но на эталонном архиве не проверена —
7-Zip отказывается создавать zip с кириллическим паролем, а другого источника
таких архивов под рукой не было. Для 7z тот же случай проверен и работает.

## Ловушки, которые стоили отладки

Все невидимы до тех пор, пока не проверишь ровно этот случай — оставлены здесь,
чтобы не наступить снова.

**Generic-права в дескрипторе безопасности.** ACE с `GR`/`GX` (GENERIC_READ,
GENERIC_EXECUTE) ядро при проверке доступа не разворачивает в конкретные права —
том молча отвечает «отказано в доступе» на всё. Нужны специфичные файловые
права: `FR`/`FX`. См. `crates/zipfs-mount/src/security.rs`.

**Наследование дескрипторов при запуске фонового процесса.** `mount --detach`
завершался, но вызвавший его скрипт висел вечно. Причина: обычный запуск
процесса отдаёт потомку все наследуемые дескрипторы, и вместе с ними —
канал вывода родителя. Родитель умирал, канал оставался открытым, читающая
сторона ждала конца потока. Лечится запуском с `bInheritHandles = FALSE`;
пароль фоновому процессу приходится передавать не каналом, а временным
файлом, который тот сразу удаляет. См. `crates/zipmount/src/mounts.rs`.

**Идентификатор процесса переиспользуется.** Список смонтированного считал
запись живой, если жив процесс с её идентификатором, — и после убийства
монтирования запись «оживала» на чужом процессе, занявшем тот же номер.
Теперь живой считается запись, у которой одновременно жив процесс **и**
существует диск.

**Развёртывание пакетов не работает с `AppData`.** Подписанный `.msix`
оттуда не ставится вовсе, а внешнее содержимое ставится, но потом COM не
находит библиотеку. Обе ошибки выглядят одинаково — «путь не найден»
(0x80070003), — хотя файлы на месте и подпись в порядке. Проверено и для
`Local`, и для `Roaming`; `%TEMP%` при этом работает, хотя лежит внутри
`AppData`. Поэтому пакет собирается во временном каталоге, а программа
устанавливается в `ProgramData`.

**GUID в манифесте пакета — без фигурных скобок.** Схема требует
`XXXXXXXX-XXXX-…` без обрамления, и привычная форма `{…}` отвергает пакет
целиком. Ошибка приходит от `makeappx`, так что ловится сразу, — но таблица
идентификаторов живёт рядом с самими COM-классами, и тест сверяет строку
манифеста с константой: разойдись они, пункт исчез бы молча.
См. `crates/zipmount-shell/src/lib.rs`.

**Класс из `SurrogateServer` не создаётся как внутрипроцессный.** Проверочный
вызов `CoCreateInstance` с `CLSCTX_INPROC_SERVER` возвращает «класс не
зарегистрирован», хотя с регистрацией всё в порядке; нужен `CLSCTX_ALL`.
Ошибка ведёт расследование совершенно не туда — в сторону манифеста и
установки пакета.

**`[INSTALLFOLDER]` заканчивается обратной косой чертой.** Переданный в
действие установщика как `--external "[INSTALLFOLDER]"`, этот слэш экранирует
закрывающую кавычку, и аргумент проглатывает всё, что идёт следом. Установка
при этом выглядит удачной — файлы на месте, ошибок нет, — а меню молча не
регистрируется. Запись `"[INSTALLFOLDER]."` отодвигает слэш от кавычки и на
смысл пути не влияет. См. `installer/ZipMount.wxs`.

**`HKEY_CURRENT_USER` в действии установщика — не обязательно нужный
пользователь.** Действие, регистрировавшее личный пакет, отработало успешно —
пакет действительно достался правильной учётной записи, — но значение реестра,
записанное тем же процессом секундой позже, в её ветви так и не появилось. Для
машинной установки `HKLM` в любом случае правильнее, а Windows Installer пишет
туда декларативно и так же убирает при удалении.

**Пункту на фоне папки не дают объектов — ему дают сайт.** Размонтирование было
объявлено для `Directory\Background` и просто не появлялось. Массив объектов
там приходит пустым — выбранных объектов и нет, — поэтому проверка, которая
прячет пункт вне наших томов, не находила пути и прятала его везде. Открытую
папку отдаёт сайт, который оболочка передаёт через `IObjectWithSite`: привести
его к `IServiceProvider`, спросить `IFolderView`, взять у него папку.
См. `crates/zipmount-shell/src/command.rs`.

**Проводник не отпускает библиотеку расширения оболочки.** Удаление молча
оставляло старую на месте, а обновление положило бы новый манифест поверх
старого кода. Windows Installer не может заменить занятый файл, и перезапуск
Проводника не спасает — он загружает библиотеку обратно сразу же, потому что
сам рабочий стол это фон папки. Лечится тем же приёмом, что и в ручной
установке: отпечаток содержимого в имени файла, и новая сборка ложится рядом
со старой, а не поверх неё.

**Процесс, запущенный из контекстного меню, приходит без `LOCALAPPDATA`.**
Список смонтированного лежит именно в этом каталоге, поэтому для такого
процесса он оказывался пустым — и обратно тоже ничего не писалось: диск,
смонтированный из меню, тем же меню размонтировать не получалось, «не числится
смонтированным» при живом диске. Теперь каталог спрашивается у системы через
`SHGetKnownFolderPath`, которому окружение не нужно, а размонтирование по букве
обходится вообще без списка: имя события остановки выводится из одной буквы.
См. `crates/zipmount/src/mounts.rs`.

**Строке-заголовку группы нужен логотип пакета, и имя файла у него особое.**
Несколько пунктов одного приложения Windows собирает в подменю с его именем и
рисует эту строку сама — значок для неё берётся у пакета, а не у обработчика.
Обычного `Square44x44Logo.png` мало: оболочка ищет вариант без подложки и под
нужный размер, по имени файла, вида
`Square44x44Logo.altform-unplated_targetsize-32.png`. Без этих файлов строка
остаётся пустой, хотя у каждого пункта под ней значок есть.

**Неизменная версия превращает каждую установку в ещё одну запись.** Код
продукта установщик выдаёт каждой сборке свой, а сравнивает версии — и пока
версия стояла на месте, повторная установка была не обновлением, а вторым
продуктом рядом с первым. В «Установленных приложениях» успело накопиться семь
строк ZipMount, и ни одну из них нельзя было снять текущим файлом `.msi`: его
код продукта уже не совпадал ни с одной. Теперь версия растёт с каждой
сборкой — см. «Сборка установщиков».

**Завершающий нуль в длине имени.** Метод `set_name` из крейта `winfsp`
дописывает `\0` и включает его в длину имени, поэтому ядро видит имя как
`file.log\0`. Префиксные маски (`file*`) при этом совпадают, а любая маска
с якорем в конце (`*.log`) — уже нет. Обходится через `set_name_raw` без нуля.
См. `crates/zipfs-mount/src/fs.rs`, `read_directory`.

**Fluent оборачивает каждое подставленное значение невидимыми знаками.** По
умолчанию он ставит вокруг каждой подстановки символы изоляции Unicode
(U+2068, U+2069), чтобы не путался текст справа налево. Консоль печатает их
мусором вокруг каждого пути и числа. Ни один из наших языков справа налево не
пишется, поэтому изоляция выключена, и тест следит, чтобы так и оставалось.
См. `crates/zipmount-i18n/src/lib.rs`.

**Узнавать ошибку по тексту — значит сломаться при первом же переводе.** Окно
поиска из контекстного меню спрашивает пароль, когда архив не открылся из-за
его отсутствия, — и понимало это по слову «пароль» в сообщении. Теперь
проблема с паролем — это тип, `PasswordError`, который находится по всей
цепочке контекста ошибки, на любом языке.

**Каталог текстов работает внутри Проводника.** Обработчик контекстного меню
берёт заголовки через тот же крейт, что и командная строка, поэтому крейту
нельзя паниковать — при `panic = "abort"` паника роняет весь Проводник — и
нельзя зафиксировать язык один раз на процесс: Проводник держит библиотеку
часами, а `zipmount language` может за это время сменить выбор. Состояние
лежит под блокировкой и заново определяется перед каждым построением меню.

**Стандартное окно установщика WiX из коробки говорит только по-английски.**
Его загрузчик ищет рядом с собой `<LCID>\thm.wxl` и `<LCID>\license.rtf` и
откатывается на встроенный английский, поэтому каждый перевод — это пара
дополнительных файлов на каждый LCID. Две мелочи стоили по пересборке: WiX
выводит идентификатор полезной нагрузки из исходного файла, так что одному
переводу на несколько LCID нужны явные идентификаторы; а RTF принимает коды
`\u` как знаковые 16-битные числа, поэтому всё выше U+7FFF — весь корейский
хангыль — нужно записывать отрицательным, иначе выйдет мусор.
